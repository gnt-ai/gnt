# Privacy-gate quality eval

A corpus of tricky cases against `applyPrivacyGate` (`apps/cli/src/privacy-gate/`)
with measured recall per category and per layer. This covers the
test-corpus/measured-recall half only -- whether to open-source the
privacy-gate module is a separate decision and isn't touched
here.

Modeled on this repo's other quality eval
(`apps/api/eval/rule_retrieval/`): a real corpus, a pure scoring harness
separate from the thing that runs it, and a README with actual measured
numbers instead of a promise. One thing is different on purpose: the
privacy gate is 100% local, deterministic/heuristic code (regex, Luhn,
compromise's NER, a character-window classifier) with no embeddings, no
reranker, and no paid API calls anywhere in its call graph. There's
nothing to precompute or replay, so unlike the rule-retrieval eval, this
one just runs for real, every time, in CI -- see "CI wiring" below.

## Layout

- `corpus.jsonl` -- 64 cases across three categories:
  - `secrets_in_prose` (22 cases) -- layer 1's detectors (keys, cards,
    SSNs, emails, phones, IPs) tested against secrets sitting inside
    realistic prose (a Slack message, a support ticket, a code comment, a
    `.env` excerpt) instead of the isolated one-line fixtures
    `test/privacy-gate/deterministic.test.ts` uses. Includes two negative
    controls (a Luhn-invalid card-shaped number, a hyphenated slug with no
    digits) documenting what must *not* get masked.
  - `policy_vs_pii` (24 cases) -- harder edge cases for layer 2b's
    policy-vs-personal classifier than `test/privacy-gate/amounts.test.ts`
    covers: new phrasings, multiple entities in one sentence, nested
    clauses, a zero-dollar figure, a possessive that lands after the
    figure instead of before it.
  - `contextual` (18 cases) -- identifiers only readable in context, with
    no name and no pattern to key off of ("the person who filed the
    original ticket", "whoever handled the case last time"). Layer 3 is a
    documented no-op today (see `layer3-contextual.ts`), so every case in
    this category is *expected* to fail right now -- see "The honesty
    line" below.
- `harness.ts` -- pure scoring: `scoreCase` and `runPrivacyGateQuality`
  compute recall and a false-positive rate, overall / per-category /
  per-layer, from a corpus case and the gate's real output. Never imports
  `applyPrivacyGate` or touches the filesystem -- see
  `test/privacy-gate/eval-harness.test.ts`, which exercises this module
  against synthetic fixtures with no real gate involved.
- `run.ts` -- the thing that actually runs `corpus.jsonl` through the real
  `applyPrivacyGate` and either prints a report or (`--write-baseline`)
  regenerates `baseline.json`. Run by hand with
  `bun run eval:privacy-gate` from `apps/cli`.
- `baseline.json` -- the recorded metrics below, generated by `run.ts`.
  `test/privacy-gate/eval-gate.test.ts` gates every `bun test` run against
  this file.

### What "recall" and "false-positive-rate" mean here

`recall` = of the values a case says must get masked, how many actually
did (exact match against a hit's recorded value, not a fuzzy compare).

`falsePositiveRate` is *not* a textbook precision score -- this corpus
doesn't annotate every non-secret token in every case as a labeled true
negative, only the specific spans a case calls out with `shouldKeep`
("this exact substring must survive untouched"). It's the fraction of
those specific spans the gate masked anyway. Read it as "how often does
the gate touch something we explicitly told it not to," not "precision
across all text this module has ever seen."

### Layer 1 (deterministic): 100% recall, 0% false positives

Every secret in every `secrets_in_prose` case got caught regardless of
where it sat in the sentence -- mid-clause, inside a code comment, inside
a multi-line config excerpt. Both negative controls (a Luhn-invalid
16-digit tracking number, a digit-free hyphenated slug) survived
untouched. This is the strongest layer, and it should be: it's the only
one with hard format validation (Luhn, SSN range exclusions, vendor
prefixes) rather than a heuristic.

### Layer 2b (amounts/policy-vs-personal): 80% recall, 0% false positives on this corpus

12 of 15 personal figures got masked correctly, and every policy figure
in the corpus stayed untouched. The three misses are real, measured gaps
in the character-window heuristic documented directly in
`layer2b-amounts.ts`, not corpus mistakes -- each one is called out by
name in `corpus.jsonl`'s own `notes` field:

- **`policy-13`** -- "he still owes $128.40" is missed because the
  possessive-pronoun check only recognizes `their`/`his`/`her`, not the
  bare nominative `he`/`she`.
- **`policy-17`** -- "Their outstanding balance across both invoices comes
  to $1,242.65" is missed because the clause between the pronoun and the
  figure (58 characters) exceeds the classifier's fixed 45-character
  `ADJACENCY_WINDOW`.
- **`policy-19`** -- "We refunded $89.99 to the customer... per her
  original request" is missed because the possessive-marker check only
  looks *before* a candidate figure; only the entity-placeholder check
  looks both directions.

One case in this corpus (`policy-07`) surfaced a real cross-layer false
positive rather than one this eval had to construct by hand: compromise's
NER tags the bare acronym "SLA" as an organization, and that placeholder's
adjacency window then pulls in two unrelated policy figures sitting on
either side of it in the same sentence ("...crosses 20% of the SLA
target, and refunds over $1,000..."). Both figures get masked even though
neither is personal. This is filed under `policy_vs_pii` with `shouldMask`
set to match what the code actually does today, not what it should
ideally do -- consistent with this eval's own premise of measuring, not
promising.

### Layer 3 (contextual): 0% recall -- the honesty line

Every single case in the `contextual` category is missed, on purpose,
because `runContextualLayer` is a documented no-op stub today (see
`layer3-contextual.ts`) -- it returns its input unchanged and reports zero
hits until a real local-model judgment pass gets wired up.
These 18 cases ("the person who filed the original ticket", "the
customer's usual delivery address", "whoever handled the case last time")
have no name and no pattern for layers 1/2/2b to catch even by accident --
that's deliberate, so this category measures exactly the gap layer 3 is
supposed to close, with nothing else muddying the number.

`test/privacy-gate/eval-gate.test.ts` asserts this recall is exactly 0
today. That's not a typo: the assertion exists so the day a real layer 3
lands, this specific test fails loudly and forces whoever
ships it to come update this README and `baseline.json` together, instead
of the corpus quietly going stale while the module gets better underneath
it.

## CI wiring

`test/privacy-gate/eval-gate.test.ts` is a normal `bun:test` file --
nothing here needed a separate eval-only script or a manual step, because
nothing in this eval costs money or hits the network. It runs every time
`bun test` runs, which now includes CI: apps/cli's `bun test` script
wasn't wired into the turbo/CI pipeline before this change (`turbo.json`
had no `test` task, and `.github/workflows/ci.yml`'s `web` job only ran
`lint typecheck build`) -- fixed here by adding a `test` task to
`turbo.json` and a bun setup step to the `web` job, so `pnpm turbo run
lint typecheck build test` now runs the full apps/cli suite, including
this eval's 64-case baseline gate, on every PR. A category or layer recall
regression fails the exact same way a broken unit test would: the build
goes red, not a stale README number nobody re-reads.

The gate test compares against `baseline.json` with a small absolute
tolerance (0.02) per metric, same shape as
`apps/api/tests/test_retrieval_eval.py` -- a floor, not exact equality, so
a legitimate tie-break or rounding difference doesn't fail the build over
noise, while an actual regression still does.
