# Rule-retrieval eval

CI-gated benchmark for `search_rules` — the path `store_client.search_rules()`
walks through apps/store's internal API (`POST /search`) into
`GntStore.search()`, which runs NativeStore's own **hybrid retrieval with a
cross-encoder reranker** (pgvector + Postgres full-text/BM25 + reciprocal-rank
fusion, then a zerank-2 rerank), shipped on for every org. This baseline
reflects that shipped path — see "Baseline provenance" below for the history
and the accepted small-scale tradeoff.

Same hit@1 / hit@3 / MRR / recall@k scoring shape as a generic
retrieval-quality harness: "caller injects a search function, harness is
pure" — mapped onto the four query families below.

## Layout

- `corpus.jsonl` — 47 rules across 6 realistic topic clusters (refunds,
  engineering conventions, escalation policy, security/access, support
  SLAs, expenses), including deliberately confusable pairs (SOC 2 vs
  ISO 27001, GDPR vs CCPA request windows, SEV1/SEV2/SEV3 escalation
  tiers) added when the corpus was hardened to evaluate hybrid retrieval —
  see "Baseline provenance" below.
- `queries.jsonl` — 81 query cases, family-tagged:
  - `exact_name` (21) — query names the rule almost verbatim
  - `paraphrase` (21) — same intent, disjoint vocabulary
  - `keyword_only` (21) — a fragment, not a sentence
  - `multi_rule` (18) — more than one seeded rule is a legitimately
    correct answer
- `harness.py` — pure scoring (hit@1, hit@3, MRR, recall@3, recall@10),
  overall and per family.
- `store_harness.py` — spawns a real apps/store instance
  (`apps/store/scripts/eval-serve.ts`) and exercises the real
  `POST /rules` (approved, signed) and `POST /search` HTTP surface.
- `fixtures/embeddings.json` — precomputed embedding for every rule and
  every query, committed. Generated by
  `apps/store/scripts/eval-generate-embeddings.ts`.
- `fixtures/rerank.json` — precomputed zerank-2 relevance score for every
  (query, candidate-document) pair the reranker sees, committed. The
  reranker ships on for every org, so the eval has to exercise it too — but a
  cross-encoder call is a real paid request, so it's recorded once and
  replayed for free, exactly like the embeddings. Generated by
  `record_rerank_fixture.py`. See `apps/store/src/testing/replay-rerank.ts`.
- `baseline.json` — recorded metrics from the last real run. This is
  what `apps/api/tests/test_retrieval_eval.py` gates future runs against.
- `generate_baseline.py` — regenerates `baseline.json` (replays both
  fixtures, no live calls). Not a pytest test, run by hand.
- `record_rerank_fixture.py` — the one-time recorder that captures
  `fixtures/rerank.json` against the live provider. Not a pytest test; the
  only thing here that makes a real rerank call, run by hand after a
  corpus/query change.

## Why the embeddings are precomputed and committed, not called live in CI

`search_rules`'s query-time embedding is a real, paid call
(`native/embed.ts`'s `zeroEntropyEmbed`, configured for
`zeroentropyai:zembed-1`). The corpus and the 81 queries are both fixed and
deterministic, so recomputing their embeddings on every CI run would mean
paying for the same vectors over and over on every PR, for no signal
gained — this codebase's existing discipline
(`apps/api/tests/conftest.py`'s `_no_real_embedding_calls` fixture and
`apps/store/src/testing/fake-embed.ts`) already treats
"never call a paid embedding API from a test loop" as non-negotiable, and
this CI-gating eval is exactly that kind of loop.

So: embeddings are computed **once**, offline, and committed as
`fixtures/embeddings.json`. `apps/store/src/testing/replay-embed.ts`
looks a vector up by exact input text and throws on a miss — the CI test
never calls any embedding function, live or fake, it replays committed
vectors through the real search code path (real Postgres/pgvector, the
real HTTP boundary) while still exercising the same code `search_rules`
runs in production.

The reranker (shipped on for every org) gets the exact same treatment. A
zerank-2 cross-encoder call is also real and paid, so `record_rerank_fixture.py`
records every (query, candidate-document) score **once**, against the live
provider, into `fixtures/rerank.json`, and
`apps/store/src/testing/replay-rerank.ts` replays those scores through the
real reranker call-site on every CI run — zero live calls, deterministic,
but the baseline still reflects the true hybrid+rerank ranking production
serves.

## Baseline provenance

`baseline.json`, `fixtures/embeddings.json`, and `fixtures/rerank.json` are
generated against the real production models — ZeroEntropy's `zembed-1`
(embeddings) and `zerank-2` (reranker), via `ZEROENTROPY_API_KEY` (set
locally in `apps/store/.env` and on the `store` Railway service in
production):

```bash
cd apps/store
bun run scripts/eval-generate-embeddings.ts --provider=real   # calls the real embedder once
cd ../api
uv run python eval/rule_retrieval/record_rerank_fixture.py     # calls the real reranker once
uv run python eval/rule_retrieval/generate_baseline.py         # records the baseline (replays both)
```

An earlier version of this baseline was generated with a lexical stand-in
(`apps/store/src/testing/hashed-embed.ts` — a real, deterministic
hashing-trick bag-of-words embedding, same family as scikit-learn's
`HashingVectorizer`) for periods with no embedding credentials available.
That version scored `exact_name`/`keyword_only` near-perfectly (shared
vocabulary) but noticeably lower on `paraphrase`/`multi_rule` (no notion
of synonymy): `paraphrase` hit@1 was 0.538 versus 1.000 with real
embeddings, `multi_rule` 0.417 versus 0.917 — an honest limitation of the
stand-in, not of the real model. `--provider=hashed` (the script's
default) still exists for testing search plumbing without a paid API
call; it's not what the recorded baseline is generated from. Re-run the
same two commands any time the corpus or query set changes.

**The corpus was hardened for hybrid retrieval, twice.** The
original 30-rule/51-query corpus scored 0.980 overall hit@1 on plain
vector search — near the ceiling, with no room for hybrid retrieval
(vector + BM25 + reciprocal-rank fusion) to show a measurable win even if
it would matter at real scale. It was grown to 47 rules/81 queries
specifically to stress vector-vs-keyword divergence: acronym/near-duplicate
confusable pairs (SOC 2 vs ISO 27001, GDPR vs CCPA request windows,
SEV1/SEV2/SEV3 tiers), distractor rules that share vocabulary with the
right answer but aren't it, and harder multi-rule queries with larger
relevant-sets. Hybrid retrieval was measured against this harder corpus
twice and both times came back a
wash-to-slight-loss against vector-only at this ~47-rule scale — hybrid
without a reranker was a hair behind, and hybrid *with* the reranker
bought overall hit@1/MRR at the cost of some multi-rule recall (a
cross-encoder optimizes for "the single best match," which fights the
multi_rule family where more than one rule is legitimately correct). On
those two reads, the call was to hold it off.

**What changed the decision.** A third, research-only eval (a free local
embedding model as a stand-in for `zembed-1`, staged single-org corpora at
1K / 10K / 100K / 1M rules) showed vector-only search degrading badly as a
corpus grows — on multi-rule and cross-department-collision queries it
nearly breaks at 100K+ (multi-rule hit@1 as low as 0.000 at one tier)
while hybrid+rerank stays functional, and the overall gap widens the
larger the corpus (at 1M rules, vector-only 0.679 vs hybrid+rerank 0.846
overall hit@1). The stand-in model makes the exact magnitudes uncertain,
but the trend — nearest-neighbor recall decaying at scale — is a
well-understood property, not an artifact.

**The decision (2026-07-17): ship hybrid retrieval with the reranker,
always-on for every org, regardless of corpus size.** The small-scale
tradeoff below (a wash on overall hit@1, a real multi_rule recall@10
regression at ~47-rule scale) is accepted deliberately, as the price of
every org being ready for the large-scale case — rather than scale-gating
the reranker on only past some corpus size. This baseline now reflects
that shipped path. The corpus stays hardened regardless; it's a strictly
better regression-catcher than the original.

## Recorded baseline (real zembed-1 embeddings + zerank-2 reranker, hybrid search)

For reference, the prior vector-only baseline is shown alongside — the
delta is exactly the accepted tradeoff: overall hit@1 / hit@3 / MRR up,
multi_rule recall down.

```
                     hybrid + rerank (shipped)                    vector-only (prior)
overall        hit@1=0.938 hit@3=1.000 mrr=0.967 r@3=0.925 r@10=0.960   (was 0.914/0.988/0.954/0.925/0.986)
exact_name     hit@1=1.000 hit@3=1.000 mrr=1.000 r@3=1.000 r@10=1.000   (was 1.000/1.000/1.000/1.000/1.000)
keyword_only   hit@1=0.952 hit@3=1.000 mrr=0.976 r@3=1.000 r@10=1.000   (was 0.952/1.000/0.976/1.000/1.000)
multi_rule     hit@1=0.889 hit@3=1.000 mrr=0.935 r@3=0.663 r@10=0.822   (was 0.833/1.000/0.917/0.719/0.938)
paraphrase     hit@1=0.905 hit@3=1.000 mrr=0.952 r@3=1.000 r@10=1.000   (was 0.857/0.952/0.917/0.952/1.000)
```

## Regenerating after a corpus/query edit

```bash
cd apps/store
bun run scripts/eval-generate-embeddings.ts --provider=real   # refresh fixtures/embeddings.json
cd ../api
uv run python eval/rule_retrieval/record_rerank_fixture.py    # refresh fixtures/rerank.json (live reranker)
uv run python eval/rule_retrieval/generate_baseline.py        # refresh baseline.json (replays both)
```

Commit the updated `fixtures/embeddings.json`, `fixtures/rerank.json`, and
`baseline.json` alongside the corpus/query change — the CI test only ever
reads the committed baseline and fixtures, it never regenerates them
itself.
